# Release Process

This document describes the release workflow for Spherepop.

## Quick Reference

```bash
# Prepare release
./scripts/release.sh 0.2.0    # Explicit version
./scripts/release.sh minor    # Auto-bump minor
./scripts/release.sh patch    # Auto-bump patch

# Push to trigger CI/CD
git push origin main
git push origin v0.2.0
```

GitHub Actions will:
1. Run full test suite
2. Verify version consistency
3. Extract changelog entry
4. Create GitHub release
5. Build distribution artifacts

---

## Prerequisites

**Before releasing**:

1. All tests pass: `make test`
2. Coverage ≥ 85%: `make test-cov`
3. Type check clean: `make type-check`
4. Lint clean: `make lint`
5. Documentation current
6. CHANGELOG.md [Unreleased] section complete

**Version policy**:
- MAJOR: Breaking changes to stable core
- MINOR: New features, provisional semantics
- PATCH: Bug fixes, documentation, infrastructure

See [CHANGELOG.md](../CHANGELOG.md) for detailed versioning policy.

## Automated Release (Recommended)

### Step 1: Prepare Release

```bash
./scripts/release.sh 0.2.0
```

This script:
- Verifies on main branch
- Checks working directory clean
- Runs test suite
- Checks coverage (warns if < 85%)
- Calls `bump_version.py`
- Updates CHANGELOG.md
- Commits changes
- Creates git tag
- Shows next steps

### Step 2: Review

```bash
git show                    # Review commit
cat CHANGELOG.md | head -50 # Check changelog
```

If incorrect:
```bash
git reset --hard HEAD~1     # Undo commit
git tag -d v0.2.0          # Delete tag
```

Then fix and retry.

### Step 3: Push

```bash
git push origin main        # Push commit
git push origin v0.2.0     # Push tag
```

GitHub Actions workflow triggers automatically on tag push.

### Step 4: Monitor

Watch GitHub Actions: `https://github.com/{user}/{repo}/actions`

Release created at: `https://github.com/{user}/{repo}/releases`

---

## Manual Release (If Script Fails)

### Step 1: Version Bump

```bash
python3 scripts/bump_version.py 0.2.0
```

Answer `y` to confirm.

### Step 2: Review Changes

```bash
git diff CHANGELOG.md
git diff pyproject.toml
```

### Step 3: Commit

```bash
git add CHANGELOG.md pyproject.toml
git commit -m "chore: Release v0.2.0"
```

### Step 4: Tag

```bash
git tag -a v0.2.0 -m "Release 0.2.0"
```

### Step 5: Push

```bash
git push origin main
git push origin v0.2.0
```

## Release Workflow Details

### GitHub Actions (`.github/workflows/release.yml`)

Triggered by: Push of tag matching `v*.*.*`

Steps:
1. **Checkout code**: Full history for changelog extraction
2. **Set up Python 3.12**
3. **Extract version**: From tag (e.g., `v0.2.0` → `0.2.0`)
4. **Extract changelog**: Section for this version from CHANGELOG.md
5. **Verify tests**: Run full test suite
6. **Verify version consistency**: Tag vs pyproject.toml
7. **Create GitHub release**: With extracted changelog as notes
8. **Build distribution**: `python3 -m build`
9. **Upload artifacts**: dist/*.tar.gz and dist/*.whl

### Version Consistency Check

Workflow fails if:
- Tag version ≠ pyproject.toml version
- Tests fail
- Build fails

This prevents accidental releases with mismatched versions.

### Release Notes Generation

Changelog section for release version extracted automatically.

Example CHANGELOG.md:
```markdown
## [0.2.0] - 2026-08-13

### Added
- Feature X with Y capability

### Changed
- Behavior Z now W
```

Becomes release notes:
```
### Added
- Feature X with Y capability

### Changed
- Behavior Z now W
```

GitHub also generates automatic "What's Changed" from commit history.

## Pre-release Versions

For alpha/beta/rc releases:

```bash
./scripts/release.sh 0.2.0-alpha.1
./scripts/release.sh 0.2.0-beta.1
./scripts/release.sh 0.2.0-rc.1
```

GitHub Actions marks these as "pre-release" automatically (detects `-` in version).

## Hotfix Releases

For urgent patch releases:

1. Create hotfix branch from tag:
   ```bash
   git checkout -b hotfix/0.1.1 v0.1.0
   ```

2. Apply fix and test

3. Release from hotfix branch:
   ```bash
   ./scripts/release.sh 0.1.1
   git push origin hotfix/0.1.1
   git push origin v0.1.1
   ```

4. Merge back to main:
   ```bash
   git checkout main
   git merge hotfix/0.1.1
   git push origin main
   ```

## Troubleshooting

### "Tests failed"

Fix tests before releasing. Run:
```bash
make test
pytest tests/ -v
```

### "Coverage below 85%"

Options:
1. Add tests to reach threshold
2. Override with `y` when prompted (not recommended)
3. Adjust threshold in `scripts/release.sh` (discouraged)

### "Version mismatch"

Tag and pyproject.toml versions differ. Causes:
- Manual edit to pyproject.toml after tagging
- Tag created before version bump

Fix:
```bash
git tag -d v0.2.0                    # Delete tag
python3 scripts/bump_version.py 0.2.0  # Re-bump
git add pyproject.toml CHANGELOG.md
git commit --amend
git tag -a v0.2.0 -m "Release 0.2.0"
```

### "Working directory not clean"

Uncommitted changes exist. Fix:
```bash
git status              # See what's dirty
git add <files>         # Stage changes
git commit -m "..."     # Commit
# OR
git stash               # Stash for later
```

### GitHub Actions fails

Check logs: `https://github.com/{user}/{repo}/actions`

Common failures:
- **Tests fail**: Fix tests, push new tag
- **Build fails**: Check build dependencies in pyproject.toml
- **Permission denied**: Check repository settings → Actions → Permissions

### Undoing a Release

If release published incorrectly:

1. Delete GitHub release (UI or API)
2. Delete tag locally and remotely:
   ```bash
   git tag -d v0.2.0
   git push origin :refs/tags/v0.2.0
   ```
3. Revert commit:
   ```bash
   git revert HEAD
   git push origin main
   ```

## PyPI Publication (Optional)

Not currently configured. To enable:

### Step 1: Add PyPI Token

GitHub repo settings → Secrets → Actions → New secret:
- Name: `PYPI_API_TOKEN`
- Value: `pypi-...` (from PyPI account settings)

### Step 2: Add PyPI Step to Workflow

Add to `.github/workflows/release.yml` after "Build distribution":

```yaml
- name: Publish to PyPI
  if: "!contains(steps.version.outputs.version, '-')"  # Skip pre-releases
  env:
    TWINE_USERNAME: __token__
    TWINE_PASSWORD: ${{ secrets.PYPI_API_TOKEN }}
  run: |
    pip install twine
    python3 -m twine upload dist/*
```

### Step 3: Verify PyPI Metadata

Update `pyproject.toml`:
```toml
[project.urls]
Homepage = "https://github.com/{user}/{repo}"
Documentation = "https://{user}.github.io/{repo}"
Repository = "https://github.com/{user}/{repo}"
Changelog = "https://github.com/{user}/{repo}/blob/main/CHANGELOG.md"
```

## Theory Status and Releases

Per OVERSOUL/PERFECTION-INFERENCE:

```
version_released ⇏ semantics_frozen
changelog_complete ⇏ no_changes_occurred
tests_pass ⇏ correctness_proven
```

Releases mark development milestones. They do not mark:
- Research completion
- Semantic finality
- Bug-free state
- Perfect implementation

Open questions (Q1-Q8 in THEORY_STATUS.md) remain open across releases.

Provisional semantics (`@pytest.mark.experimental`) remain provisional until theory resolves them.

Release automation observes the code state. It does not guarantee the code is correct, complete, or production-ready.
