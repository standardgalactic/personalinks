OVERSOUL/PERFECTION-INFERENCE

1. COVERAGE ≠ COMPLETENESS

    coverage(tests, code) = 100%
      ⇏ complete(testing)

The measurement reports what was executed.
It does not report what was not imagined.

A path exercised is not a path validated.
A validation executed is not an exhaustive specification.

100% coverage guarantees:
    every line was visited once.

100% coverage does NOT guarantee:
    every semantic corner explored,
    every precondition boundary tested,
    every interaction case enumerated,
    every future failure anticipated.

Use coverage to find gaps.
Do not use coverage to declare victory.


2. TESTS PASS ≠ SEMANTICS CORRECT

    ∀ test ∈ suite: test.status = PASS
      ⇏ implementation.semantics = correct

Tests verify claims made.
Tests do not verify claims not made.
Tests do not verify claims not yet imagined.

A passing test demonstrates:
    under the specified inputs,
    the specified outputs were observed,
    at the time the test was written.

A passing test does NOT demonstrate:
    exhaustive input coverage,
    absence of unspecified behavior,
    alignment with unwritten specification,
    robustness under future load.

Tests are samples.
Samples are not exhaustive surveys.
Exhaustive surveys are not proofs.


3. DOCUMENTED ≠ RESOLVED

    specified(x) ⇏ proven(x)
    implemented(x) ⇏ correct(x)
    tested(x) ⇏ complete(x)

Documentation records the current boundary.
The boundary is not the territory.

THEORY_STATUS.md distinguishes:
    ✓ paper-licensed,
    → implementation choice,
    ? open question.

Marking something → does not make it ✓.
Documenting ? does not resolve it.

The fact that we have written down the question
does not mean we have answered it.


4. INFRASTRUCTURE ≠ THEORY

    infrastructure_complete(R, B, D, C, A, L)
      ⇏ theory_complete(P)

Infrastructure observes.
Infrastructure SHALL NOT define.

Per OVERSOUL §0:
    P = {POP, REFUSE, BIND, COLLAPSE}
    Infrastructure observes P.
    Infrastructure does not extend P.

Completing infrastructure tasks creates:
    better tools for exploration,
    more rigorous recording,
    clearer boundary marking.

Completing infrastructure tasks does NOT create:
    resolved research questions,
    eliminated ambiguities,
    closed theoretical investigations.

When infrastructure horizon closes, report:
    remaining admissible continuations,
    unresolved questions,
    known unknowns.

Do not report:
    "project complete",
    "all questions answered",
    "nothing left to do".


5. ABSENCE OF FAILURE ≠ PRESENCE OF CORRECTNESS

    ∀ test: test ≠ FAIL
      ⇏ ∀ behavior: behavior = correct

Tests search the space of detectable errors.
Undetectable errors remain undetected.
Unimagined errors remain unimagined.

No test failed means:
    no test we wrote detected a problem we anticipated
    in the scenarios we enumerated
    at the time we wrote them.

No test failed does NOT mean:
    no bugs exist,
    no edge cases remain,
    no future input will surprise,
    no theoretical question unresolved.

The absence of observed violation ≠ proof of correctness.


6. SPECIFIED ≠ EXHAUSTIVE

    ∀ primitive ∈ P: specified(preconditions, postconditions)
      ⇏ exhaustive(specification)

Specifications document known constraints.
Known constraints are not all constraints.

SPECIFICATIONS.md records:
    what the paper states,
    what we have interpreted,
    what we have chosen.

SPECIFICATIONS.md does NOT record:
    what the paper left unstated,
    what we have not yet considered,
    what future theory may require.

A specification is a boundary marker.
It marks the boundary we currently see.

Seeing a boundary clearly ≠ seeing all boundaries.


7. HORIZON CLOSURE ≠ SYSTEM CLOSURE

    closed(infrastructure_horizon)
      ⇏ closed(system)

Closing one scope does not close all scopes.
Completing one phase does not complete the system.

Per OVERSOUL §17:
    "Upon completion of an infrastructure horizon,
     recompute the admissible continuation set."

Horizon closure triggers:
    STATUS: what is complete,
    CONTINUATION: what remains admissible,
    BOUNDARY: what is now visible that was not before.

Horizon closure does NOT trigger:
    "declare victory",
    "stop investigation",
    "assume completeness".

A CLOSED PATH IS NOT A CLOSED SYSTEM.


8. METRIC SATISFACTION ≠ OBJECTIVE ACHIEVEMENT

    coverage ≥ threshold
      ⇏ quality(testing) = sufficient

Metrics measure.
Measurements are not objectives.

Coverage percentage is:
    a derived measurement,
    not an objective function.

Per OVERSOUL §8 (TESTING):
    "Coverage percentage is a derived measurement,
     not an objective function."

Meeting a coverage threshold demonstrates:
    the measurement exceeded the threshold.

Meeting a coverage threshold does NOT demonstrate:
    tests are comprehensive,
    semantics are correct,
    quality is sufficient,
    investigation is complete.

Use thresholds to catch regressions.
Do not use thresholds to declare success.


9. CONSISTENCY ≠ CORRECTNESS

    ∀ doc ∈ {THEORY, SPEC, CODE}:
      consistent(doc_i, doc_j)
      ⇏ correct(system)

Internal consistency is necessary.
Internal consistency is not sufficient.

Documentation can be:
    internally consistent,
    thoroughly cross-referenced,
    carefully maintained,
    and still wrong.

If paper, theory status, specifications, and code all agree,
they may all agree on something incorrect.

Consistency eliminates one class of error.
It does not eliminate all classes.


10. PERFECT ≠ PERFECTIBLE

    current_state = "perfect"
      ⇏ future_improvement = impossible

Calling something perfect closes inquiry.
Closing inquiry contradicts research.

Prefer:
    "correct as specified",
    "complete for current horizon",
    "boundary clearly marked".

Avoid:
    "perfect",
    "finished",
    "nothing more needed".

Research repositories are not static artifacts.
Static artifacts do not require research repositories.
