# Spherepop Developer Guide

This guide explains the architecture, design philosophy, and common patterns. Read this to understand **why** the code is structured the way it is, not just **what** it does.

---

## 🎯 Core Philosophy

### Operations Make History; Experiments Interrogate History

```
┌─────────────────────────────────────────────────────────────┐
│  The four primitives (POP, REFUSE, BIND, COLLAPSE)          │
│  are the ONLY things that may append to Config.history.     │
│                                                              │
│  Observers (confluent, regretful, etc.) analyze histories   │
│  but NEVER modify them.                                      │
└─────────────────────────────────────────────────────────────┘
```

**Why this matters**:
- Confluence, divergence, regret are **properties discovered about histories**
- They are deliberately NOT added as a fifth Operation
- This preserves the closed four-operator algebra from the paper

**Code manifestation**:
- `spherepop/semantics.py`: Operations that construct histories
- `spherepop/observers.py`: Functions that interrogate histories
- Observers return plain values (bool, int, tuple), never `Config`

## 🔑 Key Abstractions

### Config: The Authoritative State

```python
Config = (σ, h, O, collapse_log)
```

- **σ (sigma)**: Current Sphere expression
- **h (history)**: Append-only event log (never deleted/reordered)
- **O (option_space)**: Available options (strings or Quotients)
- **collapse_log**: Provenance for COLLAPSE operations

**Immutability**: `Config` is frozen. Every operation returns a new one.

### Operation vs Event

**Operation**: A *request* to modify state (can fail validation)  
**Event**: A *committed* modification in history (what actually happened)

Why split: Clarifies the request/commit distinction.

### Quotient: Equivalence Classes

```python
@dataclass(frozen=True)
class Quotient:
    members: FrozenSet[str]
    # NO "representative" field!
```

**Critical**: A Quotient carries only membership, no privileged representative.

**Why**: Two `Quotient({a, b})` built in different orders must be equal and hash-equal.

**Consequences**:
1. **BIND**: Existential semantics (any member matches) — PROVISIONAL
2. **REFUSE**: Refusing one member refuses whole class (atomic)

See THEORY_STATUS.md Q3-Q4.

## 🎨 Design Patterns

### Pattern 1: Immutable Transitions

```python
# Good
def transition(config: Config, op: Operation) -> Config:
    return replace(config, sigma=new_sigma, history=config.history + (event,))


# Bad (mutates input)
def transition(config: Config, op: Operation) -> Config:
    config.history.append(event)  # ERROR: immutable anyway
    return config
```

### Pattern 2: Observer Non-Authority

```python
# Good: Observer
def confluent(left: Config, right: Config, policy: CollapseOp) -> bool:
    left_after = transition(left, policy)   # Analysis copy
    right_after = transition(right, policy)
    return extensional_view(left_after) == extensional_view(right_after)

# Bad: Observer that creates "the" answer
def confluent(...) -> Config:  # Don't return Config as authoritative!
    return merged_somehow(left, right)
```

## 🚨 Common Pitfalls

1. **Treating observers as operations**: Observers inform, don't prescribe
2. **Choosing Quotient representatives in semantics**: Only `views.representative()` may pick
3. **Implementing open semantics as if settled**: Mark experimental, reference THEORY_STATUS.md
4. **Mutating Config**: Always `replace()`, never mutate

## ❓ FAQ

**Q: Why are Operations and Events separate?**  
A: Operations can fail. Events represent committed history.

**Q: Why is Config immutable?**  
A: Guarantees append-only history, prevents accidental mutation, enables safe sharing.

**Q: Can I add memoization to observers?**  
A: Yes. Config immutability makes caching safe. Use `@functools.cache`, document in docstring.

**Q: How do I handle semantic questions the paper doesn't address?**  
A: Document as provisional, implement reasonable default, mark tests experimental, reference THEORY_STATUS.md.
